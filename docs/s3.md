## 1. Dataset CSV (arquivo binário obrigatório) + notificação SQS

### O que existe
Arquivo: `app/s3/s3_manager.py`, classe `S3Manager`.

Cada questão agora pode ter um **CSV de dataset** anexado, guardado ao lado dos arquivos
`.sql` já existentes:

```
s3://sqlarena-questions-bucket/questions/{question_id}/schema.sql
s3://sqlarena-questions-bucket/questions/{question_id}/data.sql
s3://sqlarena-questions-bucket/questions/{question_id}/answer.sql
s3://sqlarena-questions-bucket/questions/{question_id}/dataset.csv   <- novo (binário)
```

Como fica no mesmo prefixo, o `delete_question_files(question_id)` que já existia
**já remove o CSV junto automaticamente** — ninguém precisa mexer nisso.

### Métodos disponíveis

```python
from app.s3.s3_manager import S3Manager

s3 = S3Manager()

# Upload do CSV (aceita bytes, string ou caminho de arquivo local)
key = s3.upload_question_dataset_csv(question_id=10, csv_content=meus_bytes)

# Verificar se existe
s3.has_question_dataset(question_id=10)  # -> bool

# Ler o conteúdo de volta
conteudo = s3.get_question_dataset_csv_bytes(question_id=10)  # -> bytes

# Baixar para disco (usado pelo worker)
s3.download_question_dataset_csv(question_id=10, target_dir="/tmp/pergunta_10")
```

### Notificação ao worker (desacoplamento — Requisito 6)

Depois do upload, é necessário publicar um evento no SQS para o worker saber
que há um arquivo novo para processar:

```python
from app.sqs.queue_manager import SQSQueueManager

sqs = SQSQueueManager()
sqs.send_message(
    payload={
        "event_type": "DATASET_UPLOADED",
        "question_id": 10,
        "s3_key": key,          # retornado pelo upload_question_dataset_csv
        "file_type": "csv",
    },
    attributes={"event_type": "DATASET_UPLOADED"},
)
```

### Contrato para worker (SNS + SQS)

O worker deve escutar a fila `sqlarena-submissions-queue` e tratar mensagens com
`event_type == "DATASET_UPLOADED"` da seguinte forma:

1. Ler `question_id` e `s3_key` da mensagem.
2. Chamar `S3Manager().download_question_dataset_csv(question_id, pasta_local)` para
   buscar o arquivo.
3. Fazer "algum cálculo" sobre o CSV (exigência literal do Requisito 6 — ex: contar
   linhas, validar colunas, gerar uma estatística simples).
4. Opcional: registrar o resultado do processamento via
   `DynamoDBManager().log_crud_action("DATASET_PROCESSED", ...)`.

### Quem deve usar isso
**Quem escrever o endpoint de upload de dataset na API** chama
`upload_question_dataset_csv` e, em seguida, `send_message` para avisar o worker — as
duas chamadas andam juntas. **Responável por SNS e SQS** consome a mensagem no worker.

### Como foi validado
Rodado contra o Ministack local (`app/testes/main_s3.py`, passos 6-9): upload do CSV,
leitura de volta com validação byte a byte, envio e confirmação da mensagem na fila SQS
(contagem de mensagens disponíveis foi de 0 para 1), listagem mostrando os 4 arquivos
juntos, e exclusão removendo os 4 de uma vez.

## 2. Perguntas que o time pode receber

**"Qual é o arquivo binário obrigatório da aplicação?"**
O CSV de dataset anexado a cada questão (`dataset.csv`), armazenado no S3 junto com os
`.sql`.

**"Como o processamento do arquivo fica desacoplado do backend?"**
Via SQS: o backend só sobe o arquivo no S3 e publica uma mensagem; quem processa de fato
é um worker separado, consumindo a fila `sqlarena-submissions-queue`.

**"Isso já está na AWS de verdade ou só local?"**
Só validado no Ministack (ambiente local) até agora. O Terraform (`s3.tf`, `dynamodb.tf`)
já está pronto para aplicar na AWS Academy quando o time decidir fazer o deploy real —
basta trocar `-var-file="envs/local.tfvars"` por `-var-file="envs/aws.tfvars"`.
